# 职引 5.0 全面升级规划

更新时间：2026-09-15
范围：微信小程序、Web 求职工作台、共享数据与 AI 编排层
原则：先审计和收敛，再改代码；小程序负责发现与提醒，Web 负责管理与产出。

## 1. 规划结论

职引当前已经具备完整的求职能力，但移动端承载了过多桌面型任务。5.0 不以新增功能为目标，而以减少入口、合并对象、缩短完成路径为目标。

目标定位：

- **小程序 = 移动求职助手**：刷岗位、判断、收藏、待投递、查看进度、接收提醒、完成轻量 AI 操作。
- **Web = 求职工作台**：批量筛选、申请管线、简历和材料编辑、面试管理、计划和数据复盘。
- **AI = 求职 Copilot**：嵌入岗位、申请、面试和计划上下文，输出必须写回业务对象。
- **Data = 一套共享数据**：岗位、收藏、申请、简历版本、材料、面试、任务和提醒双端一致。

验收不看页面数量，重点看用户是否能更快完成“发现岗位 → 收藏/待投递 → 电脑处理 → 更新状态 → 手机提醒”的闭环。

| 内容服务 | 新闻、校招资讯、面经、题库、星标库 | 容易变成资讯 App | 作为岗位/申请/面试的辅助内容 |
| 机构与商业化 | agencies、VIP、机构对比 | 非主链路，入口应降级 | 我的/资源页，不进入主导航 |

### 2.3 当前核心路径

当前用户可能从首页金刚区、资源、AI 专家、校招、岗位、公司、面经等多个入口进入同一任务，常见结果是：

1. 看到岗位；
2. 在岗位、收藏、申请、进度之间反复跳转；
3. 简历、ATS、JD 匹配和申请材料各自产生结果；
4. 面试题、STAR、模拟和复盘无法自然串联；
5. 手机端承担了长文本、复杂表单和大量状态维护。

5.0 统一为：**发现岗位 → 判断匹配 → 收藏/待投递 → Web 处理申请包 → 更新申请状态 → 手机提醒下一步**。

### 2.4 移动端不合理功能

- 长文本简历编辑、Cover Letter 编辑、复杂 ATS 修改；
- 多岗位横向比较、批量改状态、复杂筛选组合；
- 复杂求职规划和大量数据录入；
- 完整 Mock Interview、长时间 AI 对话、语音复盘整理；
- Offer 深度对比、Networking 联系人管理；
- 将新闻、校招、面经、STAR、题库作为同级首页入口；
- 同一页面同时展示岗位、资讯、工具、AI、简历和面试。

## 5. 核心页面重做要求

### 首页

只回答“今天有什么值得看、我下一步做什么、我的求职到哪一步”。结构：问候与匹配岗位数 → 搜索 → 今日推荐（最多 3 组）→ 求职提醒 → 申请计数 → 3 个常用快捷入口。首页不再平铺十几个工具。

### 找岗位/岗位列表

像信息流一样浏览。首屏显示公司、岗位、地点、薪资、Experience、Sponsor、发布时间、截止时间、匹配度。卡片只保留收藏、待投递、详情三个核心动作；筛选采用底部抽屉，支持 Sponsor、地点、经验、截止时间和匹配度。

### 岗位详情

顺序固定为：基本判断信息 → 为什么推荐 → 3–6 个核心要求标签 → 精简 JD → 相关面经/公司信息。底部固定操作只保留收藏、待投递、去申请/在电脑继续、AI 分析中的主次组合。

### 求职进度

默认列表或轻量分组，不做手机 Excel。用户点开申请后只修改当前状态、下一步时间和备注；完整材料、联系人、批量操作和统计跳转 Web。

### 我的

按“个人资料、我的资产、快速练习、资源和设置”分组。简历、规划、Offer、Networking 等不再以首页工具宫格呈现。

## 6. 跨端数据同步设计

### 6.1 共享核心实体

```text
Job
 ├─ FavoriteEvent
 └─ Application
    ├─ ResumeVersion
    ├─ MatchReport / ATSReport
    ├─ ApplicationMaterial
    ├─ Contact
    ├─ InterviewRecord
    ├─ OfferDecision
    └─ NextAction / Reminder
```

### 6.2 同步规则

- 手机收藏岗位：立即写入服务端，Web “收藏/待投递”实时可见；
- 手机标记待投递：创建或更新唯一 Application，不重复生成记录；
- Web 修改状态、材料、面试时间：小程序只读同步结果并生成提醒；
- 所有状态变更带 `updatedAt`、来源端和幂等键，避免双端覆盖；
- 列表采用服务端分页、搜索和筛选；本地只缓存最近访问、收藏和提醒摘要；
- AI 结果必须带 `entityType/entityId`，保存后回写岗位、申请、简历或面试记录；
- 登录态统一 Token 刷新和退出机制，匿名收藏在登录后合并。

## 7. 代码重构顺序

### P0：先建立边界和闭环（0–2 周）

1. 建立 `Job / Favorite / Application / ResumeVersion / Interview / Task` 类型和状态枚举；
2. 统一申请 API，兼容旧接口并增加幂等更新；
3. 确定 4 Tab 导航，旧页面先保留兼容跳转，不立即删除；
4. 建立岗位列表分页、搜索、筛选、缓存和过期响应保护；
5. 统一 Loading、Skeleton、Empty、Error、Login Gate；
6. 统一岗位卡片、标签、公司 Logo、底部操作栏；
7. 完成首页、岗位列表、岗位详情、进度、我的的低保真和交互验收；
8. 增加跨端埋点：首次有效动作、收藏、待投递、Web 继续、状态更新、提醒点击。

### P1：完成 Web 工作台和主流程合并（3–8 周）

1. Web 工作台、申请看板/表格和申请详情；
2. 普通简历与简历中心合并为唯一简历资产入口；
3. ATS、JD 匹配、申请材料绑定申请和简历版本；
4. 小程序复杂入口改为结果摘要和“在电脑继续”；
5. 合并求职进度与投递追踪；
6. 规划、竞争力、技能路径合并为一份 Career Plan；
7. 题库、STAR、模拟、面试空间合并为统一训练记录；
8. AI 输出增加上下文、保存、回写和继续处理动作。

### P2：降级旧入口和优化规模化能力（9–12 周）

1. 根据 4–8 周数据决定旧页面重定向、隐藏或下线；
2. 引入长列表虚拟化评估、图片缓存、分包和请求合并；
3. 完善 Web 批量操作、日历、统计和 Offer 决策；
4. 机构、资讯、薪资、Networking 等低频能力只保留上下文入口；
5. 清理 dead code、console.log、magic number、重复 API 和硬编码；
6. 建立跨端契约测试、关键路径 E2E 和性能基线。

## 8. 删除、合并、弱化清单

### 合并

- `applications` + `job-progress` + `favorites` → 统一申请管线；
- `resume` + `resume-center` + `ats-optimize` → 简历与申请包；
- `career-planner` + `career-coach` + `skill-pathways` → 一份求职计划；
- 题库 + STAR + 模拟面试 + 面试空间 + 错题/复盘 → 面试训练记录；
- 四个 AI 专家和通用 AI → 一个上下文 AI 编排层。

### 弱化

- 新闻、校招资讯、机构、薪资、Offer、Networking、趋势：从首页和主导航移出；
- 小程序简历编辑、长文本材料、复杂规划：只显示结果和 Web 继续入口；
- 独立 AI 聊天页：保留兼容入口，但不再作为核心路径。

### 暂不删除

历史数据、旧路由和低频页面在迁移期保留；先做重定向、埋点和数据观察，避免无证据删除业务逻辑。

## 9. 量化验收标准

- 新用户 3 分钟内找到一个岗位并完成收藏或待投递；
- 岗位列表首屏可见 Sponsor、截止时间和匹配度；
- 手机收藏后 10 秒内在 Web 出现；
- Web 更新状态后小程序刷新可见，提醒不重复；
- 一条申请能看到岗位、简历、匹配、材料、面试和下一步；
- 手机端修改状态不超过 3 步；
- 首页核心入口不超过 5 个，主 CTA 每页 1 个；
- 岗位列表分页、搜索、筛选在大数据量下无明显卡顿；
- AI 结果保存/回写率、7 日回访率、重复入口跳转次数持续可观测。

## 10. 第一轮实施边界

第一轮只做：产品审计确认、核心数据模型、4 Tab 导航方案、首页/岗位列表/岗位详情/校招日历/进度/我的设计、岗位与申请同步契约、Web 申请工作台 MVP。校招日历必须与岗位截止日期和批次筛选打通，不单独建设资讯频道。暂不新增独立工具、独立 AI 产品或复杂动画，也不推倒重写现有技术栈和后端 API。
