# 本地岗位人工核验（阶段 1）

管理后台 `admin/jobs.html` 的“核验”操作只记录管理员当时看到的状态；它不探测 URL，也不保证岗位当前仍开放。仅适用于 `jobs.json` 本地岗位，不改第三方实时职位来源。

## 数据与接口

- 旧 `jobs.json` 没有 `jobVerification`/`jobVerificationAudit` 时按“未核验”读取，无需迁移。核验元数据保存在顶层 `jobVerification[岗位 ID]`，追加事件保存在顶层 `jobVerificationAudit`，不嵌入公开岗位对象。
- `GET /admin/api/jobs/:id/verification` 返回当前核验信息和历史；`PUT /admin/api/jobs/:id/verification` 写入 `{expectedVersion,status,announcementUrl,employerApplyUrl,deadline,note}`。状态为 `unverified`、`open`、`closed`、`review_needed`。`deadline:null` 表示未知。
- 删除后的审计可通过 `GET /admin/api/jobs/:id/verification/audit` 按原 ID 查询，管理页提供“查删除审计”入口。
- `PUT` 需要管理员有效账号和实时 `jobs` 权限。服务端填写操作人、时间和版本；旧版本返回 409。普通岗位新增/编辑拒绝核验字段。
- 普通岗位新增/编辑只接受列明的公开字段，校验文本类型与长度、岗位要求数组、布尔值及 URL，不能写入任意内部字段。
- 标记 `open` 时企业申请 URL 必须与公开岗位申请 URL 相同，核验截止日期须与公开截止日期相同且未过上海日期的当天。管理员应先在“编辑岗位”中修改公开字段，再核验。
- 普通编辑改变职位、公司、地点、地区、薪资、类型、行业、描述、要求、签证、Logo、公开申请 URL 或公开截止日期时，已有核验自动转为 `review_needed`，清除当前有效核验时间，记录变更前后的关键字段。删除岗位时保留墓碑事件与岗位快照；后续新岗位 ID 不复用这些已删除 ID。
- `closed` 与 `review_needed` 岗位从全部本地可浏览列表、企业关联岗位、V4 匹配岗位和兜底来源中排除；已关闭岗位即使编辑成待复核也继续隐藏，只有专用接口明确核验为 `open` 才解除保留。旧 `unverified` 岗位仍按原逻辑展示。快照游标续页会检查原快照全部本地岗位；任一岗位随后关闭就返回 410，要求重新搜索。
- 本地岗位明确截止后也按当前时间在读取时暂停展示及申请，不改写管理员核验状态：有效 `YYYY-MM-DD` 在上海日期的次日零点起生效；旧数据中的带明确时区 ISO 时间戳在截止瞬间生效。缺失、无时区或无效的旧日期不凭猜测自动暂停。到期详情保留原 `applicationStatus`，另返回 `isApplyAvailable:false` 和截止提示；公开与旧版详情、Trust、历史申请链接及快照续页按当前状态受限。管理员更改公开截止时间后重新计算；管理页新增和编辑仍只接受 `YYYY-MM-DD`。这项按需读取判断无需定时写入 `jobs.json`。
- 保存的历史岗位详情仍可打开，但关闭/待复核详情的 `applicationStatus` 是 `closed`/`review_needed`，`isApplyAvailable:false`、`applyUrl:''` 并带提示；V4 历史详情的 `officialApplyUrl`、`sourceUrl` 与 Trust 中的官网链接清空，独立 Trust 查询和新增个人观察的响应也清空当前官网链接及观察记录中的 URL，历史 Trust 评分降至风险级，旧版 `/api/jobs/detail` 本地回退申请链接也清空并标注状态。
- V4 申请看板拒绝把已关闭或待复核的本地岗位加入当前申请；原有申请记录仍可查看，但 V4 与旧版申请列表、详情、进度和工作区隐藏旧申请链接，`POST /api/v4/applications/:id/official-apply` 再次检查当前状态并返回 409。判断依据是服务端当前本地岗位 ID 和核验记录，不信任客户端提供的 `sourceType` 或快照 `source`。
- 删除后的本地岗位 ID 通过审计中的 `job_deleted` 墓碑继续识别，历史申请仍隐藏申请链接并阻止官网跳转；未曾是本地岗位的数字 ID 不受此规则影响。旧版和 V4 申请接口共用链接脱敏，覆盖 `applyUrl`、`apply_url`、`applyLink`、`job_apply_link`、`sourceUrl`、`source_url`、`officialApplyUrl`、`jobLink`、`job_link`。
- 第三方岗位须使用带来源前缀的 ID（例如 `jsearch_123`）；这类明确命名空间的外部 ID 继续可用。如果第三方裸数字 ID 恰好与一个已保留的本地岗位 ID 相同，服务端会保守拒绝本次加入/跳转，需改用命名空间 ID 后重试。此兼容取舍可防止伪造来源字段绕过本地关闭状态。
- URL 只接受 http/https，拒绝带登录凭据的地址。首次创建 `jobs.json` 时先写入并 fsync 同目录临时文件，再原子发布；后续保存使用同目录临时文件、fsync、rename 替换。四种管理员写操作在读取 JSON 前先取得共享 SQLite 数据库的写锁，以防不同进程覆盖彼此的岗位、核验和审计修改；锁超时返回 HTTP 503 并提示稍后重试。此保护要求所有写实例在同一主机的可靠本地文件系统运行本版代码，并使用同一 `DB_PATH` 和 `DATA_DIR`；跨主机部署须迁移到共享事务数据库。正式环境的实际部署拓扑仍待核对。审计记录仍与业务数据位于同一 JSON 文件，不具备防管理员直接改文件的篡改能力。

## 目前边界

核验元数据和完整审计仅在管理后台展示；公开接口只返回受限申请状态。`open` 应理解为“核验时间看到可申请”，不是“现在链接健康”。第三方实时职位不受本地核验影响。真实源覆盖率、定时链接健康探测、第三方来源过期治理和生产发布仍需单独开发和验收。

## 申请链接手动检查批次（本地候选）

- 从项目根目录运行 `node scripts/check_job_apply_links.js --run --limit 10`，单批最多 20 条。默认只选人工核验为 `open` 且企业申请 URL 与当前公开申请 URL 一致的本地岗位，优先处理尚未检查或最久未检查者；不访问第三方实时岗位。没有 `--run` 不会开始检查。尚未接入 cron、PM2 定时任务或后台启动按钮。
- 每个 URL 最多 10 秒，整批约 60 秒预算，剩余候选计入 `deferred`，可在下一批继续处理。只允许 HTTP/HTTPS 标准端口，不接受登录凭据；逐跳重新检查域名解析出的**全部**地址，拒绝本地、私网、保留地址和非安全重定向；连接固定到校验过的 IP，不使用代理，最多跟随 3 次重定向。先发 HEAD，遇 405/501 再发 GET，仅读响应头，不下载正文。
- 当前结果存在 `jobs.json` 顶层 `jobApplyLinkHealth[岗位 ID]`：记录原 URL 哈希、检查开始时间、结果、HTTP 状态码、重定向次数及原因；管理后台“申请链接检查”列和人工核验弹窗仅展示与**当前**企业 URL 一致的结果。写入前在共享 SQLite 写锁内再核对岗位、人工核验状态和 URL，过时探测不会覆盖新链接或较新的结果；删除岗位时一并清除其健康结果。
- `reachable` 仅表示当时 HTTP 可访问，不保证申请表单仍开放；404/410 标为“疑似失效，需人工复核”；403/429、5xx、超时及网络错误均为“结果不确定”；被安全规则拒绝的地址需人工核对。检查结果**不会自动改变人工核验状态或公开申请权限**，管理员仍需查看原公告和企业页面，再人工更新核验记录。
- 本轮只用受控 DNS/传输及本地 HTTP server 验证，未真实探测公网或部署定时任务。真实岗位池覆盖率、运营重试和处理时效仍待开发和验收。

## 定时执行入口（默认关闭，本地候选）

- 可由运维定时器按小时调用 `JOB_LINK_CHECK_SCHEDULE_ENABLED=1 node scripts/check_job_apply_links.js --scheduled --limit 10`。未设置开关时，`--scheduled` 返回 `schedule_disabled` 和非零退出码；普通 `--run` 仍是显式人工复查，不受定时冷却限制。本代码不会自行安装 cron 或在后端启动时自动检查。
- 每个上海时区小时最多成功完成一批；领取与完成记录保存在 `jobs.json` 顶层 `jobApplyLinkSchedule`，通过原有共享 SQLite 写锁跨进程串行化。执行中租约为 5 分钟，同时触发返回 `skipped`；失败不记成功，进程崩溃后租约到期可在同一小时重试。旧执行者不能完成已由新执行者领取的批次。脚本以 `ran`／`skipped`／`failed` 报告结果，失败返回非零退出码。
- 定时模式只选择当前 URL 最近 24 小时未检查的候选岗位，最多 20 条；因此小岗位池不会每小时重复访问企业站。人工模式可在需要时立即复查。批次仍受原有约 60 秒预算和单 URL 最长 10 秒约束，检查结果不会自动改变人工核验或公开申请状态。
- 上线前须核实所有写实例同主机、共用 `DB_PATH` 与 `DATA_DIR`，并配置运维定时器、日志与失败告警；真实企业站点探测频率和运营处理时效仍需验收。本轮未安装定时器、未运行公网检查或生产部署。

## 用户岗位纠错的后台分流（本地候选）

- 官网继续向既有 `POST /api/feedback` 提交 `type=岗位信息纠错` 与一段用户填写的内容；本轮不改提交契约和数据库表。反馈管理新增这一类型的筛选，后台列表只对符合官网既有格式的内容派生原因、岗位 ID 和用户自报来源；不符合格式的历史反馈仍按普通文本显示。
- 用户自报 ID 和来源只作为待核查线索。当前管理员的令牌与实时账号都必须具有岗位管理权限，且服务端确实能找到对应的本地岗位或 `job_deleted` 审计墓碑，才提供“打开本地岗位核验”或“查看已删除岗位审计”入口；没有岗位管理权限时明确提示无入口，外部来源和无法匹配的 ID 不伪装为本地岗位。若本地岗位文件暂不可读，反馈列表仍可使用，只隐藏候选入口并提示稍后重试。外部纯数字 ID 仍可能与本地岗位撞号，即使出现同 ID 的本地候选，也必须核对标题、来源和原公告，不能据此确认归属。跳转参数仅接受安全范围内的正整数。
- 反馈管理页面转义所有用户文本；打开核验页面也不会自动修改岗位或反馈处理状态。管理员需查看原始公告、企业页面和现有核验/链接检查证据，再手动更新岗位核验与反馈处理状态。正式运营的处理时效、结果审计和真实来源闭环仍待开发及线上验收。

## 岗位纠错处理审计与耗时（本地候选）

- 新增 `0023_feedback_handling_audit.sql` 后，反馈具有 `review_version`；每次实际改变状态或管理员备注，都在同一 SQLite 立即事务中递增版本并追加一条 `feedback_handling_events`，记录前后值、实时管理员账号及 ISO 时间。提交 `PUT /admin/api/feedbacks/:id` 必须携带当前 `expectedVersion`，过时返回 409；状态和备注完全相同则不新增事件。令牌权限与实时账号 `feedback` 权限均须有效。
- `GET /admin/api/feedbacks/:id/audit` 可分页读取处理记录。迁移前的反馈保留原状态和备注，但没有可追溯事件；迁移前已完成的反馈显示“历史处理时间未记录”，不能把 `updated_at` 或迁移后仅修改备注的时间当成处理完成时间。列表对未完成反馈显示“距提交”，数值是提交到当前时间的总历时，重开后也如此；已完成且有从未完成状态进入完成状态的审计事件时，显示提交到最近一次此类事件的历时。此指标不是队列等待时长或 SLA 达标率；旧 SQLite 无时区 `created_at` 明确按 UTC 解释。
- 岗位纠错标记 `resolved` 或 `ignored` 时需填写 10–1000 字处理说明，说明是反馈处理依据，不会自动修改 `jobs.json` 或岗位核验。尚未应用迁移或审计表缺失时，列表仍可读取，但页面禁用保存，写入接口返回 503，拒绝无审计更新。隔离数据库专项验证版本冲突、旧记录、权限、故障回滚及删除级联；真实数据库未应用迁移。
- 保留既有反馈硬删除语义：删除反馈会连同其处理事件级联删除，页面明确警告。需要长期留存运营审计时，应先设计独立留存与隐私删除规则，再修改删除策略；当前事件不是不可删除的合规归档。
- 正式环境上线前须备份数据库、审批并运行受控迁移，完成发布门禁和授权测试；未迁移时正式 `deploy.sh` 的待迁移检查会阻止发布。本地实现与测试不代表生产迁移、部署或线上验收。
