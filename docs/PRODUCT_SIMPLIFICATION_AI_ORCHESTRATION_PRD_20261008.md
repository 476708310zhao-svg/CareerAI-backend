## 1. 产品结论

职引下一阶段不应继续增加工具入口，而应从“求职工具集合”升级为“围绕一次求职申请推进结果的 AI 工作台”。

核心原则只有三条：

1. **一个主对象**：所有求职动作尽量归属到一条 `application`（岗位申请）。
2. **一个上下文 AI**：用户只看到一个 AI 助手；岗位顾问、申请助手、面试教练、职业规划师作为内部能力路由，不再要求用户选择专家。
3. **一个明确下一步**：首页和申请详情优先回答“我现在最应该做什么”，而不是展示功能目录。

本轮属于**体验架构重构**，不是后端推倒重来。现有申请工作区、持久 AI 会话、简历版本、材料草稿、面试空间、Today 任务等后端能力大部分可以复用。

### 1.1 当前实现快照（2026-10-10）

| 范围 | 当前事实 |
|---|---|
| 一级导航 | 已固定为首页、找岗位、进度、资源中心、我的五个 Tab |
| 申请主链路 | Web 与小程序围绕 `application` 关联工作台、下一步、任务、简历、材料、面试和时间线 |

## 2. 背景与问题

### 2.1 重构前问题（历史决策背景）

本轮重构启动时，产品存在以下结构性问题。这些条目用于说明决策来源，不代表 2026-10-10 的当前实现；当前事实以 1.1 节和已提交运行代码为准：

- 资源中心共 29 个入口，其中 23 个工具、4 个服务、2 个 AI 入口，用户需要先理解产品结构才能完成任务。
- 同一目的至少存在 14 组重复入口，例如简历、规划、面试、AI 助手在多个页面重复出现。
- AI 被拆成四位专家、通用助手、多个 AI 工具、欢迎区和全局悬浮入口，增加选择成本。
- 首页同时承载搜索、轮播、今日任务、会员横幅、岗位推荐、校招资讯等内容，主行动不明确。
- 存在人工映射的 75–98 匹配分、硬编码“最近对话”、固定“思考阶段”等不诚实反馈。
- 旧页面、新页面和重复业务链路并存，用户资产与上下文容易割裂。
- 部分 AI 跨对象写入缺少清晰预览或统一确认语义。

### 2.2 用户核心任务

用户真正需要的不是“使用某个工具”，而是完成以下连续任务：

```text
发现岗位 → 判断是否适合 → 加入申请 → 准备简历/材料
→ 正式投递 → 准备笔试/面试 → 跟进结果 → 复盘并调整
```

产品结构、AI 上下文和数据模型都应围绕这条链路组织。

## 3. 目标与非目标

### 3.1 产品目标

- 用户进入首页后 10 秒内能识别当天最重要的一个动作。
- 用户从岗位进入申请后，无需在多个工具页重复选择公司、岗位、简历和材料。
- AI 自动读取当前申请上下文，用户无需手动选择“哪个专家”。
- 所有 AI 写入在发生前说明“将改什么”，高风险行为始终由用户亲自完成。
- 现有用户数据、旧链接和五个主 Tab 在迁移期内保持可用。
- 通过 4–8 周数据验证后，再决定是否下线旧入口。

### 3.2 业务目标

- 提升“岗位浏览 → 创建申请”的转化率。
- 提升“申请创建 → 完成下一步任务”的转化率。
- 提升 AI 建议被采纳并完成的比例，而非单纯提升 AI 对话次数。
- 降低重复入口跳转、无结果浏览和中途退出。

### 3.3 非目标

- 本期不建设新的通用 Agent 平台或工作流市场。
- 本期不让 AI 自动投递、外发消息、付款、退款或删除用户数据。
- 本期不重建现有申请、简历、材料和面试数据模型。
- 本期不取消五个主 Tab，也不立即删除旧页面。
- 本期不把“AI 生成内容”包装为客观事实、精确概率或真实内部思考过程。

## 4. 目标信息架构

### 4.1 五个主导航保持不变

| Tab | 新定位 | 首要任务 | 不再承担 |
|---|---|---|---|
| 首页 | 今日行动台 | 完成一个最重要动作 | 工具陈列、会员广告堆叠 |
| 岗位 | 机会发现 | 找到并加入合适岗位 | 分散的申请准备工具 |
| 进展 | 申请工作台 | 推进每条申请的下一步 | 仅做状态列表 |
| 资源 | 内容与资产库 | 找测评、笔试、面试和行业资料 | 29 项工具入口大厅 |
| 我的 | 个人资产与设置 | 管理简历、权益、偏好和隐私 | 重复业务工具导航 |

### 4.2 页面关系

```text
首页“今日最重要动作”
          │
          ▼
     某条申请工作台 ◄──────── 岗位“加入待投递”
          │
          ├── 下一步行动
          ├── 简历版本
          ├── 申请材料
          ├── 笔试/测评资料
          ├── 面试空间
          ├── 任务与时间线
          └── 上下文 AI

资源中心 ── 提供可复用内容/资料 ──► 关联到申请
我的 ───── 提供个人资产/偏好 ───► 供申请工作台调用
```

### 4.3 核心实体

- `job`：机会来源和岗位事实。
- `application`：用户求职进程的主对象。
- `resumeVersion`：不可变简历版本，可关联申请。
- `material`：已确认的申请材料。
- `interviewSpace/session/report`：面试准备、练习和报告。
- `todayTask`：从申请或规划中抽出的今日动作。
- `aiConversation`：可选绑定申请的持久上下文会话。

实体引用必须遵循 `docs/CORE_ENTITY_REFERENCE_CONTRACT.md`，不得用页面本地缓存替代服务端主数据。

## 5. AI 产品形态与操作边界

### 5.1 用户只看到一个 AI

用户入口统一命名为“问 AI”或“AI 帮我推进”。系统根据当前页面、申请状态和用户输入，在后台选择能力，不展示 `job_advisor`、`application_assistant`、`interview_coach`、`career_planner` 等内部类型。

AI 默认上下文优先级：

1. 当前申请及岗位事实；
2. 当前关联简历版本；
3. 已确认的申请材料；
4. 最近面试报告；
5. 用户主动提供的本轮信息。

联系人、待确认草稿及无关敏感资料默认不进入上下文。

### 5.2 AI 自主等级

| 等级 | 允许行为 | 用户交互 | 示例 |
|---|---|---|---|
| L0 只读 | 检索、总结、排序、解释 | 无需确认 | 总结 JD、解释岗位要求 |
| L1 草拟 | 生成候选内容，不写入主数据 | 用户查看/编辑 | 草拟求职信、面试回答 |
| L2 确认后写入 | 写入低风险、可追踪对象 | 必须展示明确预览并确认 | 新建 Today 任务、申请任务、修改下一步 |
| L3 用户执行 | 涉及外部影响或关键状态 | AI 只导航和辅助 | 官网投递、发送消息、付款、退款、删除 |

### 5.3 首版可执行动作白名单

P0 仅开放已有能力支撑的动作：

- 创建 Today 任务；
- 创建申请任务；
- 更新申请“下一步行动”；
- 保存申请备注；
- 创建简历 AI 修改建议，用户逐条确认后生成新版本；
- 创建申请材料草稿，用户确认后保存。

以下行为必须保持用户亲自执行：

- 修改申请状态；
- 正式投递或对外发送消息；
- 完成付款、退款；
- 删除或归档关键数据；
- 替用户承诺面试时间、薪资或入职决定。

### 5.4 统一确认体验

每次 L2 写入必须展示：

- 动作对象：将修改哪条申请/简历/材料；
- 动作名称：例如“新增申请任务”，禁止只写“执行操作”；
- 变更前后：新增内容或旧值 → 新值；
- 影响范围：是否会同步 Today、申请时间线等；
- 按钮：`确认新增/确认修改` 与 `取消`；
- 结果反馈：成功后提供查看入口；失败时不制造已完成假象。

简历继续使用“待确认 change set → 新建不可变版本”；材料继续使用“pending draft → 确认/拒绝”，不强行合并底层协议。

## 7. 模块需求明细

### 7.1 首页：今日行动台

#### 页面顺序

1. 问候与简短状态摘要；
2. “今天最重要的一步”卡片；
3. 其他 Today 任务，最多 2 条；
4. 与目标岗位相关的推荐；
5. 校招资讯/内容，置于首屏之后。

#### 主行动生成规则

- 有临近截止且未投递申请：优先准备/投递相关任务；
- 已投递且有笔试/面试时间：优先临近节点；
- 存在用户手动置顶任务：尊重用户选择；
- 无申请时：引导搜索岗位或导入机会；
- 无真实动作时：展示明确空状态，不创建虚假紧迫感。

#### 验收

- 首屏不同时出现两个同等级主 CTA；
- 卡片说明“为什么现在做”；
- 点击直达对应申请/任务，而不是中间工具大厅；
- 关闭推荐或无数据时布局不塌陷。

### 7.2 岗位：机会发现

- 保留搜索、筛选、校招日历和岗位详情。
- 主 CTA 统一为“加入待投递”或“查看申请进展”。
- 重复加入时返回已有申请，不重置已有阶段。
- 匹配展示改为证据标签，例如“技能覆盖 4/6”“缺少英语要求证明”，不使用无依据的 98 分。
- 官网投递只负责打开官网并记录点击，不宣称已经替用户投递。

### 7.3 进展：申请工作台

#### 列表页

- 保留状态筛选：全部、准备中、已投递、笔试、面试、Offer、已结束。
- 每张卡只突出：公司/岗位、当前阶段、截止或最近节点、一个下一步行动。
- 次要字段折叠，不在卡片上放置完整工具集合。

#### 详情页

推荐信息层级：

1. 当前状态与最近节点；
2. 推荐下一步；
3. 准备包：简历、材料、测评/笔试、面试；
4. 任务；
5. 时间线；
6. 联系人和备注；
7. 上下文 AI。

工作台数据优先复用：

```http
GET /api/v4/applications/:id/workspace
```

小程序新增 `getApplicationWorkspace(id)` API 包装即可，P0 不另建聚合接口。

### 7.4 上下文 AI

#### 入口

- 申请详情：“问 AI”固定入口；
- 首页主行动：“让 AI 帮我准备”；
- 简历/材料/面试页：带当前对象和申请上下文进入同一会话体系；
- 不保留全局悬浮球。

#### 会话能力

- 创建或恢复绑定申请的会话；
- 加载历史消息；
- 发送时使用 `requestId` 防重复；
- 同一会话只允许一个 pending turn；
- 支持取消；
- 回答中标注信息不足，不编造招聘事实。

#### 回答结构建议

- 结论；
- 依据；
- 建议下一步；
- 可执行动作卡（如有）。

不得展示虚构的“AI 正在检索、深度推理、专家会诊”等固定动画文案。

### 7.5 简历与材料

- 所有入口统一到 Resume Center。
- AI 修改先生成 change set，逐条展示原文、建议和理由。
- 用户确认后创建新版本，旧版本不可覆盖。
- 申请材料先生成可编辑草稿，确认后保存并关联申请。
- 待确认草稿不得作为已完成资产用于下游生成。
- 材料生成若缺少事实，必须向用户提问或留占位，不得编造数字和经历。

### 7.6 面试

- 每条申请最多使用一个主面试空间承载准备上下文。
- 支持开始练习、提交回答、完成/取消、查看报告。
- 完成操作前展示跨对象影响：生成报告、创建复练任务、是否更新申请下一步。
- 若暂不改后端事务协议，P1 先将副作用准确告知用户；不得以静默写入作为最终体验。

### 7.7 计划与 Today

- 职业规划提供方向和阶段目标，不再作为另一套待办系统。
- 可执行项统一进入 Today 或申请任务。
- `GET` 接口必须只读；任务生成由明确的 `sync` 或用户触发动作完成。
- Today 任务必须尽可能带 `applicationId`、`jobId` 或来源说明。

### 7.8 资源中心

栏目调整为：

- 测评资料；
- 笔试题库；
- 面试经验；
- 公司/行业内容；
- 我的收藏；
- 我的已购。

资料详情显示适用公司/岗位/届别、内容目录、更新时间、来源/版权说明、试看、价格与售后说明。购买与交付规则详见 `ASSESSMENT_RESOURCE_COMMERCE_PRD_20261008.md`。

资源内容应支持“关联到申请”或从申请工作台进入相应筛选结果，但不得把资料购买伪装成申请成功的必要条件。

### 7.9 我的

保留：

- 个人资料与求职偏好；
- 简历资产；
- 已购与收藏；
- 会员/权益；
- 消息设置；
- 隐私、数据与账户设置；
- 帮助与反馈。

移除重复的 AI 专家、规划、模拟面试和材料工具入口。

## 8. API 与数据方案

### 8.1 P0 直接复用

| 能力 | 现有接口 |
|---|---|
| 申请工作区 | `GET /api/v4/applications/:id/workspace` |
| 申请详情/编辑 | `GET /api/v4/applications/:id/detail`、`PATCH /api/v4/applications/:id` |
| 申请任务 | `POST /api/v4/applications/:id/tasks`、`PATCH /api/v4/applications/:id/tasks/:taskId` |
| AI 会话 | `/api/ai/conversations` 及 turns/cancel 子路由 |
| Agent 建议确认 | `/api/v4/agents/tasks` 及 retry/cancel/confirm 子路由 |
| Today | `/api/v4/today/tasks`、`sync`、`defer` |
| 简历建议 | `/api/v4/resumes/:id/ai-change-sets` 及 confirm/reject |
| 材料草稿 | `/api/v4/materials/drafts` 及 confirm/reject |
| 面试 | `/api/v4/interviews/spaces`、sessions、answers、complete/cancel |
| 埋点 | `POST /api/analytics/events` |

### 8.2 P0 必要改动

- 小程序 `miniprogram/utils/api-v4.js` 增加 `getApplicationWorkspace(id)` 包装。
- Agent `writeAction` 增加服务端白名单和非法动作错误响应。
- 新增产品埋点事件，不新建独立分析服务。
- 客户端 feature flag 增加新版首页、申请工作台和上下文 AI 的规范化字段。
- 将小程序旧通用助手逐步迁移到持久 AI 会话 API。

### 8.3 暂不承诺的能力

当前不存在，不能在页面文案中作为已支持能力：

- 通用 `executeAction(actionType, payload)` 编排 API；
- AI 自动修改申请状态；
- AI 自动投递、发消息、付款、退款或删除；
- Agent 单任务查询、分页筛选或可靠后台任务队列；
- 完整 PII 匿名化；
- 真正的百分比灰度分桶。

### 8.4 数据与隐私

- 模型输入执行字段级最小化与已知格式脱敏，不宣称“所有敏感信息已匿名化”。
- 姓名、地址、学校、公司和自由文本敏感事实需要后续补充策略。
- 日志避免记录完整 prompt、联系方式、证件号和银行卡号。
- 新表只能通过 migration 增加，禁止在 route 或 service 中运行 DDL。
- 上线前使用正式 migration runner 核对目标环境：`schema_migrations` 必须完整登记当前 `0001–0011` 的全部 migration，且 `pending=0`；禁止手工只执行某一个 SQL 文件。预发/生产状态尚未验证，也未获得 apply 授权。

## 9. 埋点与成功指标

### 9.1 核心事件

| 事件 | 触发点 | 关键属性 |
|---|---|---|
| `primary_action_viewed` | 首页主行动曝光 | applicationId、actionType、reason、variant |
| `primary_action_clicked` | 点击主行动 | applicationId、surface、sourceEntry |
| `application_workspace_viewed` | 进入申请工作台 | applicationId、state、entry |
| `application_next_action_completed` | 完成推荐下一步 | applicationId、actionType、duration |
| `context_ai_opened` | 打开上下文 AI | applicationId、surface |
| `ai_suggestion_generated` | AI 返回可执行建议 | conversationId、actionType |
| `ai_action_previewed` | 展示确认卡 | applicationId、actionType |
| `ai_action_confirmed` | 用户确认写入 | applicationId、actionType、result |
| `ai_action_cancelled` | 用户取消 | applicationId、actionType、reason |
| `legacy_entry_redirected` | 旧入口重定向 | oldRoute、targetRoute、paramsPreserved |

所有新事件增加 `eventVersion`；服务端事实事件继续作为申请状态、付款和面试完成等关键漏斗的唯一真相来源。

### 9.2 北极星与阶段指标

**北极星指标：每周完成有效下一步的活跃申请数。**

阶段指标：

- 首页主行动点击率；
- 创建申请后 24 小时内完成首个准备动作的比例；
- 申请详情到任务完成转化率；
- AI 建议 → 预览 → 确认写入转化率；
- 用户从旧入口跳回新主链路的比例；
- 7 日内继续推进同一申请的比例。

护栏指标：

- AI 未授权写入数必须为 0；
- AI 动作重复写入率；
- 工作台加载失败率和 P95 时延；
- 旧链接失败率；
- AI 取消后仍显示完成的比例；
- 用户投诉、退款和隐私事件。

不以“对话条数”“页面入口点击总数”作为主要成功指标。

## 11. 上线策略与回滚

### 11.1 上线顺序

1. 预发环境与内部账号；
2. 新版入口开关默认关闭，完成数据校验；
3. 按客户端版本或测试名单启用；
4. 观察 3–7 天后扩大范围；
5. 全量后保留旧页面兼容层 4–8 周；
6. 满足下线门槛后再删除重复实现。

### 11.2 回滚

- 页面级异常：关闭对应 feature flag，恢复旧入口。
- AI 异常：关闭可执行动作，仅保留只读问答。
- workspace 异常：降级为现有 application detail。
- 数据异常：停止写入类功能，不自动批量修复；先审计事件和数据库记录。
- 支付/交付异常：遵循商业化 PRD 的熔断与人工补发流程。

## 12. Definition of Done

一个功能项只有同时满足以下条件才算完成：

- [ ] 有明确用户问题和唯一主行动。
- [ ] 页面在加载、空数据、错误、无权限和离线状态下可用。
- [ ] API 响应遵循统一 `{ code, message, data }` 约定。
- [ ] 涉及 AI 写入时，确认前不改变主数据。
- [ ] 涉及实体引用时使用统一 refs，不用模糊 ID。
- [ ] 关键事件可在服务端或分析系统验证。
- [ ] 新旧入口兼容与参数传递已测试。
- [ ] 自动化测试和微信真机验收通过。
- [ ] 文档、事件表、开关和回滚说明同步更新。
- [ ] 不包含虚假分数、虚假历史、虚假思考或虚假完成状态。

## 13. 风险与待评审决策

| 决策 | 建议 | 原因 |
|---|---|---|
| 首页会员横幅是否保留 | 移出首屏，仅在权益相关场景出现 | 避免打断核心任务 |
| AI 是否保留四专家品牌 | 内部保留能力路由，用户侧合并 | 降低选择成本且不浪费现有提示词 |
| 申请状态是否允许 AI 修改 | P0 不允许 | 状态影响漏斗和后续自动化，应由用户确认事实 |
| 面试完成是否自动创建任务 | 改为完成前预览，后续统一确认 | 重构前存在静默跨对象写入；当前实现已要求预览和明确确认 |
| 资源中心何时删除工具入口 | 新主链路稳定 4–8 周后 | 避免旧用户找不到功能 |
| 是否立即做通用 action schema | P0 不做，先用白名单适配 | 当前可执行动作少，先验证价值 |
| 是否做百分比灰度 | 有稳定用户分桶后再做 | 当前 rollout 记录不等于真实分流 |
