# 职引小程序：当前功能盘点与后续开发规划

> 盘点日期：2026-11-12
>
> 盘点对象：`jobapp-server` 主仓库中的微信小程序、共用后端、Web 工作台与管理后台。
>
> 判断依据：当前源码、`miniprogram/app.json`、`DEVELOPMENT_STATUS.md`、相关功能及发布文档。本文描述的是**仓库当前能力**；没有重新登录生产环境、运行微信真机验收或核验当前线上版本。

## 一、产品现状

职引已经形成“找机会 → 加入申请 → 准备简历和材料 → 跟进投递 → 准备笔试面试 → 复盘”的求职流程。当前小程序底部实际注册的五个入口是**首页、机会、AI求职、资源、我的**；申请进度由首页、我的及相关二级页面进入。较早文档中的“首页、岗位、进度、资源、我的”是历史产品方案，不能当作当前导航事实。

项目采用微信原生小程序、Node.js/Express、SQLite 和静态管理后台。Web 工作台复用部分申请业务接口。主仓目前有大量未提交改动，近期开发记录中的“本地完成”不等于已进入正式小程序或生产后端。

状态口径：

- **已有实现**：当前仓库存在页面、接口或服务代码；仍可能需要联调、数据和验收。
- **本地待验收**：代码或开发预览已完成，但缺少微信真机、生产迁移或正式发布证据。
- **受限开放**：有配置、审核、授权或内容门槛，不能仅凭页面存在就认为所有用户可用。

## 三、当前最重要的缺口

1. **发布状态不统一。** 主仓有大量未提交改动，功能横跨小程序、后端、迁移、后台和测试。应建立一次明确的候选版本清单，逐项标记“仅本地、开发预览、后端已上线、小程序已上线、真机已验收”，避免混合发布或对外误报。
2. **核心链路缺少端到端验收。** 优先以真实测试账号走通“搜索岗位 → 加入申请 → 选简历/材料 → 打开官网 → 本人确认已提交 → 更新状态 → 提醒/面试/报告”；覆盖弱网、切账号、两台设备、过期岗位和错误状态。
3. **简历 AI 真实效果仍未闭环。** 完成模型超时候选的发布评审与服务端验证，再用本人账号复测 PDF 打开、资料提取、评分、建议生成、确认保存和额度返还。记录失败原因与耗时，不把规则兜底当作模型成功。
4. **刷题内容供给和发布门槛尚未满足。** OCR 草稿需要明确的人工确认及审计、批量建题能力；题库公开还要求真实授权、独立审核、私有原件安全检查和真实设备验证。单人快速核对目前有实施计划，不能称为已完成的批量审核功能。
5. **支付与商业化需分线验收。** 先核验 9 元资料的真实下单、取消、成功回调、领取与退款撤权；会员价格契约和资质未定前保持会员新销售关闭。不要从后端支付开关推断小程序正式版已开放。
6. **数据与运营质量待持续验证。** 定期检查岗位来源、更新时间、失效链接、官方申请地址和校招截止日；申请转化指标只统计可对账的用户确认事实，缺数据时显示未知。

## 四、建议的后续开发顺序

| 优先级 | 工作包 | 可验收的完成标准 |
| --- | --- | --- |
| P0 | 收口当前工作区和发布基线 | 将现有改动按业务主题梳理、评审并形成候选版本；对应迁移、配置、页面及测试都有清单；`check:release` 在固定快照通过。 |
| P0 | 核心求职链路真机联调 | Android/iOS 和至少两个账号覆盖岗位、申请、简历、材料、确认提交、状态历史、提醒；错误与离线状态可恢复，跨账号无数据串露。 |
| P0 | 简历 AI 与原 PDF 闭环 | 模型超时修复经过独立验证和发布；真机打开本人原 PDF，评分/建议可完成或明确失败，确认前不改原简历，超时不无限加载。 |
| P1 | OCR 快速核对与内部题库 | 实现疑点队列、版本绑定的人工确认审计、幂等批量建题；以隔离库样本量测耗时和错题，仍不自动公开。 |
| P1 | 首批授权刷题内容与灰度 | 准备真实授权题目，完成来源和内容审核、生产存储/扫描及备份恢复；网页与微信双端验收通过后仅开放明确批准的免费题集。 |
| P1 | 岗位数据与运营可靠性 | 建立来源故障、链接失效、过期、回退数据和对账异常的可见监控；用真实样本校准匹配解释与提醒节奏。 |
| P2 | 9 元资料与人工服务运营 | 真实购买交付及售后验收；人工服务工单验证授权、撤销、管理员处理与交付，确认是否需要独立定价。 |
| P2 | 会员与浏览器插件 | 会员价格/权益/退款规则和真实支付资质确定后再灰度；插件先完成真实 Greenhouse/Lever 表单兼容与隐私验收，再考虑发布。 |

## 五、执行时的验收与记录方式

- 每个工作包记录：功能入口、后端接口、数据库迁移、配置开关、测试结果、微信开发者工具/真机结果、实际上线版本、负责人及日期。
- 后端变更运行相关专项测试与 `npm test`；小程序变更运行 `npm run check:miniprogram`。发布候选运行 `npm run check:release`，并独立完成数据库备份/迁移/回滚演练和微信真机验收。静态检查不能替代真机与真实支付。
- 对 AI、岗位、题目和运营指标分别标注“真实来源 / 规则或模板 / 待人工确认 / 不可用”，避免将推断结果展示为事实。
- 上线顺序建议为：固定候选快照 → 隔离测试 → 预发布数据与设备验收 → 后端及迁移 → 小程序上传提审 → 上线观察。每一步保存版本和验证证据。
