## 1. 文档目的

本阶段建设官网用户侧 Web 的三个核心模块：

1. 申请管理工作台；
2. 申请详情与申请包；
3. Web AI 专家问询。

Web 端定位为“求职管理中心”，负责长时间使用、批量整理、长文本编辑、横向比较和结果复盘。微信小程序定位为“随身求职助手”，负责快速查看、提醒、状态更新、刷题和面试前练习。

两端共用同一套后端数据，不复制岗位、申请、简历、计划和面试记录。小程序现有资源中心继续完整直出，不在本项目中改为隐藏或折叠。

## 2. 当前基础与边界

### 2.1 已有基础

- 小程序已将首页、个人中心、每日任务和使用指南统一到申请管线；
- 申请详情已具备申请包入口；
- JD 匹配、简历、申请材料、面试空间和 AI 报告已支持上下文传递；
- AI 求职规划、竞争力陪跑和每日简报已统一为同一求职计划的不同视图；
- 现有自动化测试 208/208 通过，`check:miniprogram` 通过；
- 后端已有 Web 登录和 V4 业务接口；
- `admin/` 是管理后台，不作为普通用户 Web 前端使用。

### 2.2 本阶段不做

- 不重做小程序资源目录；
- 不新增独立的 AI 专家入口；
- 不在 Web 首期开发完整社交网络、职业洞察和技能路径工作台；
- 不改变会员、支付和权益规则；
- 不删除低频功能，是否降级或下线留到用户验证阶段；
- 不让 AI 自动覆盖简历或申请材料，所有写入仍需用户确认。

## 3. 产品目标

用户打开 Web 后，应能在一个工作台完成以下任务：

1. 看见需要处理的申请和今日任务；
2. 筛选、排序和批量更新申请；
3. 进入单条申请查看岗位、简历、匹配、材料、面试和下一步；
4. 在当前申请上下文中询问 AI 专家；
5. 将 AI 建议保存为申请材料、计划任务或面试准备事项。

首期目标不是增加页面数量，而是减少以下问题：

- 同一岗位出现多个申请记录；
- 用户在岗位、简历、申请材料和面试页面之间重复填写；
- 用户不知道一条申请下一步该做什么；
- AI 回答与当前岗位或申请脱节；
- Web 和小程序看到的状态不一致。

### 5.2 页面上下文参数

跨页面和跨端跳转统一使用以下标识：

```text
jobId

```

申请详情进入 AI 专家时，至少传递 `applicationId`。服务端根据申请记录补充岗位、简历、材料和面试上下文，前端不自行拼接另一套数据。

### 5.3 申请状态

```text
interested    感兴趣（看板“已收藏”列）
preparing     准备申请
applied       已申请
oa            在线测评（看板“笔试中”列）
phone_screen  电话面试
interview_1   一轮面试
interview_2   二轮面试
final         终面
offer         Offer
rejected      已拒绝
withdrawn     已撤回
```

状态选项和允许转换由现有 V4 状态机下发；“面试中”“已结束”仅用于看板分组，不能作为接口状态写入。单条和批量更新复用同一服务，记录历史并复用已有面试空间与漏斗事件逻辑；本批不新增状态自动提醒规则。

## 6. 模块一：申请管理工作台

### 6.1 工作台 `/dashboard`

首屏只回答三个问题：

1. 哪些申请需要处理？
2. 哪些申请临近截止或需要跟进？
3. 今天最应该完成哪项准备？

页面模块：

- 待处理申请数量；
- 临近截止申请；
- 今日任务和面试提醒；
- 最近更新的申请；
- “处理下一项任务”主按钮；
- 进入完整申请管线的次按钮。

工作台不展示完整资源工具宫格，资源仍从资源中心进入。

### 6.2 申请管线 `/applications`

支持两种视图：

- 看板：按申请状态分列；
- 表格：适合筛选、排序和批量操作。

表格字段：

- 公司；
- 岗位；
- 申请状态；
- 截止日期；
- 下一步行动；
- 使用的简历版本；
- 最近更新时间；
- 联系人或面试标记。

筛选条件：

- 状态；
- 公司；
- 截止日期范围；
- 是否有下一步任务；
- 是否进入面试；
- 是否有 Offer。

批量操作：

- 修改状态；
- 设置截止日期；
- 设置下一步行动；
- 批量归档；
- 批量添加标签。

批量操作必须显示影响条数，并支持撤销或恢复。

### 6.3 申请管线数据接口

优先复用：

- `GET /api/v4/applications/board`；
- `POST /api/v4/applications`；
- `PATCH /api/v4/applications/:id`；
- `GET /api/v4/today/tasks`；
- `GET /api/companies`。

如果现有接口不支持批量状态更新，新增批量接口时应保持单条状态机规则一致，不允许前端绕过服务层直接写状态。

## 7. 模块二：申请详情与申请包

### 7.1 申请详情 `/applications/:applicationId`

页面顶部固定显示：

- 公司和岗位；
- 当前申请状态；
- 截止日期；
- 下一步行动；
- 最近更新时间；
- “问 AI 专家”按钮。

页面主体分为五个区域：

1. 岗位与 JD；
2. 申请包；
3. 申请进展；
4. 面试与 Offer；
5. 活动记录和备注。

### 7.2 申请包

申请包是申请详情的核心区域，集中展示：

- 当前使用的简历版本；
- JD 匹配结果；
- ATS 检查结果；
- Cover Letter；
- Recruiter 消息；
- Follow-up 文案；
- 其他已确认申请材料。

每个材料卡片必须显示：

- 材料类型；
- 关联岗位；
- 使用的简历版本；
- 状态：草稿、待确认、已确认、已归档；
- 最近更新时间；
- 打开、编辑、复制和归档操作。

### 7.3 申请详情快捷动作

只保留与当前申请直接相关的操作：

- 修改状态；
- 设置下一步任务；
- 选择简历版本；
- 重新进行 JD 匹配；
- 打开申请材料；
- 进入岗位面试空间；
- 问 AI 专家。

不在详情页重复放置独立的“简历中心”“职业规划”“通用 AI 工具”大入口。

### 7.4 申请详情接口

优先复用：

- `GET /api/v4/applications/:id/detail`（保留小程序兼容）；
- `GET /api/v4/applications/:id/workspace`（Web 聚合）；
- `PATCH /api/v4/applications/:id`；
- `GET /api/v4/resumes`；
- `GET /api/v4/resumes/:id/versions`；
- JD 匹配相关 V4 接口；
- 申请材料相关 V4 接口；
- `GET /api/v4/interviews`。

已实现聚合接口：

```text
GET /api/v4/applications/:id/workspace
```

该接口在只读事务中读取已有实体，返回 `application/history/contacts/tasks/materials/match/resume/drafts/jdReport/interviews/refs/availability`。响应 `Cache-Control: no-store`，不创建简历版本、不运行 AI。

- 材料先匹配明确的 `application_id`；没有明确申请关联的旧材料，才匹配非空岗位/客户端标识。明确属于其他申请的材料不会混入。
- `resume.version` 读取当前申请关联版本，校验版本、简历和用户归属。
- `jdReport` 只展示当前岗位和当前简历版本的历史检查结果；未关联版本或没有对应记录返回 `null`。
- `offer` 当前为 `null`，`availability.offer=not_integrated`，独立 Offer 条款仍在后续阶段。

### 7.5 批量状态接口（已实现）

`POST /api/v4/applications/bulk-status`

```json
{
  "items": [
    { "id": 123, "status": "preparing", "historyId": 456 },
    { "id": 124, "status": "preparing", "historyId": 457 }
  ],
  "status": "applied"
}
```

- `items` 为 1～50 条不重复的申请，`historyId` 取自最新看板或详情响应。
- 先验证所有记录的用户归属、当前状态和历史版本，再在事务中写入；任一记录失败则整批不生效。
- 成功响应含 `changed/unchanged/results`，以及 `undo.historyIds/expiresAt`；无变化的记录不产生重复历史。
- `POST /api/v4/applications/bulk-status/undo` 接收 `{ "historyIds": [458, 459] }`。只允许本人本次批量写入的历史，10 分钟内且没有后续状态变化才可撤销；任一冲突则整批不撤销。
- 撤销保留面试空间与既有记录，追加纠正历史，不删除审计证据。
- 单条 `PATCH /:id/status` 兼容旧小程序请求；Web 额外传 `expectedState: {status, historyId}` 防止旧页面覆盖新状态。

## 8. 模块三：Web AI 专家

### 8.1 入口与上下文

AI 专家在以下位置可进入：

- Web 全局 AI 专家入口；
- 工作台任务卡；
- 申请详情；
- 申请包材料卡片；
- 面试复盘页。

全局入口允许用户选择上下文。上下文页面进入时，默认使用当前对象，不再要求用户重新填写公司和岗位。

### 8.2 Web 端能力

- 询问岗位匹配和投递策略；
- 分析简历与 JD 的差距；
- 生成申请材料草稿；
- 设计面试准备方案；
- 解读面试报告和错题；
- 比较求职方案或 Offer；
- 把回答保存为申请备注、计划任务或面试准备事项。

### 8.3 交互要求

- 左侧显示当前岗位和申请摘要；
- 中间显示对话；
- 右侧显示可引用的简历、JD、材料和面试结果；
- 每条 AI 输出标明关联对象；
- 生成类结果先进入预览状态；
- 写入申请、简历、计划或面试记录前必须由用户确认；
- 支持重试、取消和错误说明；
- 不向用户展示模型名称、内部提示词或技术参数。

### 8.4 AI 接口与安全

优先复用：

- `/api/ai`；
- V4 AI Runtime 和 Agent 接口；
- 现有 AI 配额、脱敏、超时、降级和 kill switch 机制。

Web 端必须继承小程序已有规则：

- 敏感信息进入模型前脱敏；
- 超时、429、5xx 和非法响应显示可重试状态；
- AI 失败不产生空白成功结果；
- 未确认内容不写入正式资产；
- 配额不足时给出明确的剩余额度或升级提示；
- 所有写入记录 `source=web` 和关联对象 ID。

## 9. Web 与小程序协同

### 9.1 两端保留的能力

- AI 专家问询；
- 申请状态快速更新；
- 面试题库、STAR、OA 练习；
- AI 模拟面试；
- 竞争力陪跑的任务执行；
- Today、提醒和错题复练。

### 9.2 Web 主操作、小程序轻入口

- 简历中心；
- Networking Copilot；
- AI 求职规划；
- Offer 对比；
- 公司情报；
- 职业洞察；
- 技能路径。

小程序资源页继续完整展示这些功能，卡片点击后可以进入轻量页面或引导到 Web 深度处理。

### 9.3 同步要求

- Web 修改申请状态，小程序刷新后立即可见；
- 小程序完成 Today 任务，Web 工作台同步完成；
- Web 保存 AI 结果，小程序在对应申请或面试页面可查看；
- 冲突按服务端更新时间和现有同步规则处理；
- 所有跨端跳转保留 `applicationId` 等上下文参数。

## 13. 风险与处理

| 风险 | 处理方式 |
|---|---|
| Web 与小程序状态不一致 | 只允许服务端状态机写入，统一更新时间和引用 ID |
| 申请详情请求过多导致空白 | 增加申请工作区聚合接口，并为各区块提供独立加载状态 |
| AI 回答脱离当前岗位 | 强制传递 `applicationId`，服务端生成上下文摘要 |
| 用户误把草稿当正式材料 | 材料状态明确区分草稿、待确认和已确认 |
| 功能继续膨胀 | 新功能必须挂到岗位、申请、简历、计划或面试对象下 |
| 低频功能过早删除 | 先保留入口并记录使用数据，4～8 周后再决策 |
| Web 首期范围过大 | 先完成申请管线、申请包和 AI 专家，其他资源只做关联入口 |

## 14. 开发完成定义
