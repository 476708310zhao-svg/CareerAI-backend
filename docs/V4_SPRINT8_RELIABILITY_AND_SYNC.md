# Sprint 8：提醒可靠性、跨设备一致性与收藏请求统一

> 完成日期：2026-09-09
> 范围：提醒派发、Today、收藏/岗位截止提醒、小程序收藏请求层
> 边界：未运行微信 E2E、未调用真实 AI、未发送真实微信消息、未应用生产 migration、未推送或部署

## 1. 本批解决的问题

- 提醒派发从“逐条串行、发完再记账”改为有投递账本的有界并发处理，避免两个 cron 同时发送同一提醒。
- 站内消息 ID 在网络请求前原子写入投递账本；微信失败重试时只重试微信，不重复创建站内消息。
- 派发只扫描目标日期至未来 30 天，支持 batch、游标分页、90 秒租约、最多 5 次重试、并发上限 5 和结构化耗时埋点。
- 派发脚本会按游标续跑并汇总结果；存在失败或页数截断时返回非零退出状态。
- Today 本地任务同步改为增量合并，不再删除另一台设备没有上报的任务；带 `updatedAt` 的旧状态不能覆盖较新的服务端状态。
- 小程序对服务端 Today 结果做最终状态回写；请求飞行期间若用户产生新操作，新版本继续保持 pending。
- 收藏增加本地 outbox、稳定 `operationId`、服务端操作回执和删除 tombstone；服务端按客户端更新时间处理冲突。
- 收藏工具及收藏页普通 JSON 请求统一进入 `api-client`，不再自行拼接 Token、401 和 `wx.request`。
- 岗位截止日期更新会生成包含新日期的 delivery key，旧日期的记录不会阻止新提醒。

## 2. 新增持久化结构

`0006_sprint8_reliability.sql` 只创建表和索引：

- `reminder_deliveries_v4`：投递键、状态、尝试次数、租约、站内消息 ID、微信状态和安全错误类别。
- `favorite_sync_v4`：收藏当前状态、删除 tombstone、客户端更新时间和必要展示 payload。
- `favorite_operations_v4`：按用户记录唯一操作 ID，重复补传不会重复执行。

生产应用前仍需 Human 完成明确数据库目标、备份、恢复验证和 migration checksum 审核。

## 3. 冲突与重试规则

### 提醒

1. `(reminder_id, delivery_key)` 唯一。
2. worker 先取得租约，再原子创建或复用站内消息。
3. 微信失败时状态为 `failed`，后续最多重试 5 次。
4. `sent` 状态和旧 `sent_keys` 都能阻止重复发送。
5. 测试环境关闭外部通知、微信未配置或 openid 不可用时，站内消息完成后微信记为 `skipped`，不无限重试。

### Today

1. 同步是增量 upsert，不把“本设备没上报”等同于删除。
2. 有客户端时间时采用 last-write-wins；较旧设备只能读取服务端最终状态。
3. 只有请求对应的本地版本仍未变化时才清除 pending，避免误确认后续操作。

### 收藏

1. 同一收藏键在本地 outbox 中只保留最新操作。
2. 重试沿用相同 `operationId`；服务端只执行一次。
3. 删除保存 tombstone，其他设备不会把旧本地收藏重新上传复活。
4. 服务端较新状态覆盖客户端；客户端仍有待同步新操作时，本地状态暂时优先。

## 4. 可观察性与隐私

`reminder_dispatch_completed` 只记录数量、耗时、并发和 batch 大小，不记录 openid、Token、用户文本或密钥。投递失败只保存有限错误类别，不保存微信响应正文。
