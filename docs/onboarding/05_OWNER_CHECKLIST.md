# 仓库维护者交付清单

这份清单由维护者填写。仓库公开，**不要在本文件、Issue 或 PR 中填写账号密码、密钥、测试用户个人资料或生产地址的私密参数**。

## 发出邀请前

- [ ] 确认公开仓库中的代码、文档和历史记录适合新成员查看；确认合作范围、代码归属和保密安排。
- [ ] 确认新成员的 GitHub 用户名与联系人，并通过 GitHub 仓库协作者功能邀请；不要共享个人 GitHub 账号。
- [ ] 指定开发基线 `codex/release-20261116`、首个任务 ONBOARD-01、PR 审阅人和沟通渠道。
- [ ] 核实 GitHub 对 `main` 与开发基线的保护设置：PR 审阅、CI 必需检查、禁止强制推送；当前公开仓库未发现 ruleset，branch protection 需在设置页人工核实。
- [ ] 本包的 PR 模板目前位于开发分支；若希望 GitHub 自动填充，另行审查并将模板同步至默认 `main`。保持业务分支分开不妨碍单独同步该文档。
- [ ] 确定是否需要 `CODEOWNERS`，取得实际 GitHub 用户名后再配置，不在模板中写不存在的账号。

## 环境与权限

- [ ] 首个任务只提供仓库访问；若后来需要微信预览、AI 或职位源，单独提供测试 AppID、测试账号与最小范围凭据。
- [ ] 测试账号和虚构样本与生产用户、生产库、生产支付、真实简历分离；记录由谁发放、何时收回。
- [ ] 生产密钥、生产数据库、服务器和微信正式发布权限只由指定发布负责人持有。
- [ ] 确认 CI 在新成员 PR 上运行；若平台权限或费用限制阻断 CI，记录替代的本地验证和审阅要求。

## 第一周交接

- [ ] 新成员完成 [ONBOARD-01](04_FIRST_TASK.md) 的环境复现并报告命令与结果。
- [ ] 维护者给下一项功能任务填写明确的文件范围、接口契约、验收方式和 PR 目标。
- [ ] 双方约定同步频率、文件冲突处理、代码审阅时限与上线审批人。
- [ ] 对照 [当前状态](01_CURRENT_STATE.md) 核对生产后端和小程序实际版本，避免把快照分支或代码检查结果当作上线证明。

GitHub 个人账号仓库的协作者权限粒度有限；如果长期需要不同角色分别管理代码、审阅和设置，可评估将仓库放入组织后再配置角色。仓库访问与分支规则以 GitHub 设置页当时实际状态为准。
