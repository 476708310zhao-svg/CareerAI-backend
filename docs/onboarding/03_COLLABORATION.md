# 协作与提交约定

## 分支和任务

1. 维护者为每项任务指定开发基线、目标 PR 分支、负责人、文件范围、验收标准及审阅人。当前默认开发基线与 PR 目标是 `codex/release-20261116`；`main` 保持分开。GitHub 新建 PR 时默认可能选 `main`，提交前要手动核对 **base** 是任务书指定分支。
2. 开发者从指定基线新建 `feat/<主题>`、`fix/<主题>` 或 `docs/<主题>` 分支。一个 PR 处理一个主题；不要直接推送 `main` 或发布分支。
3. 修改前在 [DEVELOPMENT_STATUS.md](../../DEVELOPMENT_STATUS.md) 的“当前文件占用”登记负责人、任务和路径；多人需要同一文件时先约定顺序。完成并提交后记录验证、释放占用。
4. 每次提交只包含该任务文件。提交前执行 `git status --short --branch` 和 `git diff --check`，检查新增文件、凭据、数据库、上传目录及构建产物。

## PR 应提供

- 改了什么、为什么、用户会看到什么；关联任务及目标分支。
- 实际运行的命令、退出码和跳过项；小程序 UI 改动附同版本预览或截图及真机状态。
- 接口、数据结构、权限、迁移、配置或第三方调用的变化；对应兼容、回滚和验收方式。
- 尚未验证的内容明确写“未验证”。PR 描述可先复制 [模板](../../.github/pull_request_template.md)；GitHub 自动填充模板需该文件进入默认分支，目前 `main` 尚未包含本包。

维护者审查通过且 CI 通过后再合并。若 CI 失败、存在未解决的高风险问题或生产前置条件缺失，保留 PR 并继续修复。当前仓库尚未以文档替代 GitHub 设置；仓库规则、必需检查与审阅权限由维护者在 GitHub 核实和配置。

## 高风险和发布边界

| 范围 | 额外要求 |
| --- | --- |
| 登录、鉴权、支付、Webhook、上传、用户数据 | 在任务书与 PR 中单列风险、权限边界和回归方式；不使用真实用户数据做开发样本。 |
| 数据库迁移 | 先写版本化 migration；用隔离数据库验证升级、失败回滚与旧数据；生产 apply 由发布负责人另行决定。 |
| 微信小程序 | 记录预览版本和后端基线；正式上传、提审、真机验收需单独排期。 |
| 生产部署及密钥 | 新成员默认不持有生产密钥、生产库和部署权限；发布由指定负责人执行，遵循 [部署文档](../production-deploy.md)。 |

沟通时优先在任务或 PR 中写可复现的结论。环境凭据和测试账号通过维护者指定的受控渠道分发，不进入公开仓库。仓库本身是公开的，Issue、PR、提交及附件都按公开材料处理。
