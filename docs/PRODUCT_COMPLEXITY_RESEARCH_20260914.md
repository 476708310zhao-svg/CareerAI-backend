# 职引小程序功能复杂度与产品收敛方案

## 执行结论

职引当前的问题不是页面数量本身，而是多个独立功能都在争夺同一个求职任务。产品已经具备找机会、准备材料、管理申请、准备面试、职业决策、内容服务、AI 辅助七类能力，但用户真正需要完成的是一条连续链路：

**找到值得投的岗位 → 准备这次申请 → 跟进申请状态 → 准备下一轮面试。**

建议把产品边界收敛为四个核心模块：

1. **机会**：校招日历、职位、公司、JD 匹配。
2. **申请包**：一套简历/经历资产，支撑 ATS 检查、岗位定制和申请文案。
3. **申请管线**：收藏、投递状态、截止提醒、面试和 Offer。
4. **面试与 AI**：题库、STAR、模拟、复盘，以及围绕上述三类数据的 AI 辅助。

职业规划、竞争力诊断、每日简报应成为横跨四个模块的行动层，而不是四套相互独立的计划产品。Networking、薪酬、Offer 对比、机构测评和资讯可以保留为补充能力，但不应继续扩张为新的主线。

资源中心继续完整直出。优化重点是产品边界、命名和数据复用，不是把目录藏起来。

## 现状盘点

当前主导航有 5 个入口：首页、资源、进度、AI 专家、我的。这个数量本身可接受，问题在于每个入口内部又承载了大量同级能力。

资源中心包括校招日历、规划与材料 5 项、面试与笔试 4 项、职业决策 4 项、内容服务 3 项。AI 专家页有岗位顾问、申请助手、面试教练、职业规划师四个角色，并同时提供申请材料、面试空间和通用咨询入口。产品地图还包含普通简历、简历中心、ATS 优化、项目复盘、技能路径、职业洞察、每日简报、Networking、Offer 对比等独立页面。

真正的复杂度来自三种重复：

- **同一个对象有多套管理流程**：普通简历、简历中心、ATS 简历分析分别存在不同操作路径；申请进度和投递追踪也存在两个页面。
- **同一个结果有多个生成入口**：竞争力陪跑、AI 求职规划、技能路径、职业规划师都能生成目标、差距和行动计划。
- **同一个训练目标有多个产品名称**：面试题库、STAR 案例、AI 模拟面试、面试空间、错题本、语音复盘分别覆盖内容、练习和复盘，但用户需要自行理解它们的关系。

有些相似入口不是真重复：

- 面试题库是公共内容学习，个人面经是收藏或发布自己的记录；
- ATS 是简历与岗位的文本检查，JD 匹配是投递判断；
- STAR 是回答结构，错题本是个人复练记录；
- 薪酬查询是市场信息，Offer 对比是具体录用决策。

这些应通过统一数据和路径衔接，而不是简单删除。

## 功能收敛矩阵

| 能力 | 判断 | 建议 |
|---|---|---|
| 校招日历、职位搜索、公司库 | 机会发现，核心 | 保留，岗位详情统一进入申请 |
| JD 匹配 | 投递前判断，核心 | 保留，结果直接创建或关联申请 |
| 普通简历、简历中心 | 管理流程重叠 | 以简历中心作为唯一资产底座 |
| ATS 优化、申请材料 | 简历/申请子能力 | 并入申请包，绑定具体申请 |
| 求职进度、投递追踪 | 申请状态重叠 | 统一为一个申请管线 |
| 竞争力陪跑、AI 规划、技能路径 | 计划生成重叠 | 合并为一份可更新计划 |
| 每日简报 | 复访与汇总入口 | 保留，读取同一份任务和申请数据 |
| 面试题库、STAR | 内容学习 | 保留，统一进入面试准备 |
| AI 模拟面试、面试空间 | 训练流程重叠 | 合并为一次面试训练记录 |
| 错题本、语音复盘 | 训练附属结果 | 挂在训练记录下 |
| Networking | 留学生差异化能力 | 保留，绑定公司和申请 |
| 薪酬、Offer 对比 | 低频决策支持 | 保留为申请/Offer 工具 |
| 公司洞察、职业洞察 | 数据可信度要求高 | 暂停扩张，先验证数据来源 |
| 机构测评、资讯 | 非主链路 | 保留内容入口，降低主流程权重 |
| 通用 AI、四位 AI 专家 | 与结构化工具重叠 | 统一 AI 编排层，结果写回核心模块 |

## 外部证据与启示

Nielsen Norman Group 对 Progressive Disclosure 的定义是将高级或低频功能延后到次级界面，使应用更容易学习、减少错误。[1] 这不要求资源目录必须隐藏；对职引更适合的用法是资源页完整展示，但首页和任务流程只围绕当前下一步行动组织。

NNGroup 的移动端研究强调，提示、可见的操作线索和清晰的手势能够降低用户记忆负担。[2] 因此“面试题库 → 模拟 → 报告 → 错题复练”应由系统自动串联，不能要求用户记住多个入口名称。

复杂应用的可用性原则把“识别优于回忆”和“系统状态可见”列为关键原则。[3] 用户应在申请详情中直接看到所用简历版本、匹配报告、材料草稿、面试状态和下一步行动，而不是在多个页面之间回忆数据在哪。

Teal 将 AI 简历构建器、针对岗位的多版本简历和集中式申请追踪放在一个求职系统中。[4] LinkedIn 的公开求职路径也把保存岗位、提醒和 Job Tracker 组织在 Jobs 入口下，申请状态按 Saved、In Progress、Applied 等阶段管理。[5] 这些产品的共同点是围绕岗位/申请对象形成工作台，而不是把每项能力做成孤立工具。

## 目标产品结构

### 首页：只回答“今天做什么”

首页保留今日任务、关键提醒、校招更新和少量推荐。每个用户优先看到一个主行动，例如补充档案、完成简历、处理截止申请或进行面试复练。

### 资源：完整工具目录

资源页保持完整展示，继续按规划与材料、面试与笔试、职业决策、内容服务分组。卡片描述统一采用“使用时机 + 产出”格式，减少同义名称造成的理解成本。

### 进度：唯一申请对象

每个岗位只对应一个申请对象，关联岗位公司、收藏和提醒、当前状态、简历版本、JD 报告、申请文案、联系人、面试结果和 Offer 决策。“求职进度”和“投递追踪”最终应合成一个页面和一套数据模型。

### AI 专家：一个入口，四种上下文

四位专家可以作为内部角色保留，但用户不需要先理解四个产品。岗位详情默认进入岗位顾问，申请详情默认进入申请助手，面试记录默认进入面试教练，计划页默认进入职业规划。AI 输出写回申请、简历、面试记录或 Today 任务，并显示关联对象。

### 规划：一份计划，多个视图

保留一份计划对象，包含目标岗位、能力差距、阶段里程碑、每周任务和证据。竞争力评分、技能路径、3/6/12 月计划和每日简报读取这份计划的不同视图。

## 0–90 天路线图

### 0–14 天：定义边界和观测基线

建立功能清单和唯一对象关系，统一下一步行动字段和状态文案；增加首次进入、首次完成、重复生成、跨页跳转、结果保存等埋点。暂不删除页面和历史数据。

### 15–45 天：合并简历与申请

将普通简历和简历中心统一到一个入口。ATS、JD 匹配和申请材料绑定到具体申请与简历版本。申请详情增加材料包区域。旧入口先保留兼容跳转。

### 46–70 天：合并规划与 Today

以竞争力陪跑的任务模型作为计划主线。AI 求职规划和技能路径改为生成或更新计划内容。每日简报只汇总计划、申请、截止提醒和面试任务。

### 71–90 天：合并面试训练

题库、STAR、模拟面试、面试空间共享一个训练记录，报告、错题、语音复盘挂在记录下。观察一个完整周期后，再决定是否下线旧入口。

## 验证指标

- 首次进入到完成第一个有效动作的时间；
- 完善档案后进入岗位、申请或简历动作的比例；
- 一个申请从岗位查看到材料生成的完成率；
- 同一用户在多个简历/规划入口之间来回跳转的次数；
- AI 结果被保存或关联到申请的比例；
- 面试训练后再次复练的比例；
- 7 日内回访并完成任务的比例；
- “找不到”“不知道选哪个”“重复填写”等反馈占比。

没有数据证明某功能低频前，不建议直接删除。先并入主流程、停止新增独立入口，再用 4–8 周数据决定保留、降级或下线。

## 最终建议

职引应从“功能集合”变成“求职工作台”。资源目录可以继续完整存在，但产品主线只维护一套岗位、一套申请、一套简历资产、一套面试记录和一份求职计划。

第一优先级是合并简历/材料和申请管线；第二优先级是合并规划体系；第三优先级是合并面试训练。机构、资讯、趋势和更多 AI 能力在前三项稳定前暂停扩张。
